## Agent Kurulamayan Cihazların İzlenmesi, Wazuh ile Syslog Yapılandırması ve Sistem Zafiyet Yönetimi

### 1. Wazuh ile Syslog Yapılandırması
Bugünkü staj çalışmam kapsamında ilk olarak, agent kurulamayan ağ cihazlarının (Firewall, Switch vb.) ürettiği logların **Syslog** protokolü üzerinden toplanabilmesi amacıyla Wazuh sunucusunda gerekli yapılandırma işlemlerini gerçekleştirdim. 

Bu doğrultuda, sunucunun dış logları alabilmesi için `ossec.conf` dosyasına yeni bir `<remote>` bloğu ekleyerek aşağıdaki tanımlamaları yaptım:
- **Bağlantı Tipi:** `syslog`
- **Port:** `514`
- **Protokol:** `udp`
- **IP Kısıtlaması:** `"any"` (tümü)

### 2. Sistemin Devreye Alınması ve Sorun Giderme (Troubleshooting)
Sistemin devreye alınması ve test edilmesi sürecinde çeşitli teknik sorun giderme adımları uyguladım. Yönlendirilen test loglarının Wazuh'a ulaşmaması üzerine yaptığım analizde, **WSL2** sanal ağ (NAT) köprüsünün `UDP/514` paketlerini düşürdüğünü tespit ettim. 

Bu sorunu aşmak için:
- Test loglarını doğrudan Wazuh konteynerinin içinden ateşleyerek ağ katmanını aradan çıkardım ve konfigürasyonu izole bir şekilde test ettim.
- Konteyner imajının minimal yapısı nedeniyle `logger` aracının bulunmaması durumunu, herhangi bir bağımlılık yaratmamak adına **Linux bash kabuğunun** yerleşik yönlendirme yeteneklerini kullanarak çözdüm. 
- Ayrıca, Wazuh Decoder'ın standart Syslog başlığına (Tarih, Hostname vb.) ihtiyaç duyması nedeniyle ham metinlerin alarm üretmediğini gözlemledim. Bunun yerine sistemin `514` portunu başarıyla açtığını Manager'ın kendi başlangıç logları üzerinden doğruladım.

Çalışmanın bu bölümünü sonlandırırken, test amacıyla WSL üzerindeki `rsyslog` servisine eklediğim geçici yönlendirme kurallarını, gelecekte log çakışmasına yol açmaması için temizleyerek laboratuvar ortamını orijinal haline döndürdüm.

### 3. Sistem Zafiyet Yönetimi ve CVE Analizi
Çalışmamın ikinci bölümünde ise ajan kurulu makinelerdeki güncel güvenlik açıklarının (CVE) tarama sonuçlarını analiz ederek sistemin yama planlamasını yaptım. Bu kapsamda `wsl-agent` (Ubuntu 24.04.4 LTS) makinesi üzerinde **Wazuh Vulnerability Detector** modülü ile gerçekleştirdiğim güncel taramada **"Kritik" (Critical)** seviyede herhangi bir bulguya rastlanmamıştır. 

Yaptığım tekilleştirme analizi sonucunda aksiyon alınması gereken **2 adet "Yüksek" (High)** seviyeli zafiyet tespit ettim.

## Monitoring Agentless Devices, Syslog Configuration with Wazuh, and System Vulnerability Management

### 1. Syslog Configuration with Wazuh
As part of my internship work today, I first performed the necessary configuration processes on the Wazuh server to collect the logs generated by agentless network devices (Firewall, Switch, etc.) via the **Syslog** protocol.

To this end, I added a new `<remote>` block to the `ossec.conf` file to allow the server to receive external logs, defining the following parameters:
- **Connection Type:** `syslog`
- **Port:** `514`
- **Protocol:** `udp`
- **Allowed IPs:** `"any"` (all)

After successfully transferring this edited configuration file to the Docker container, I restarted the Wazuh service to activate the new listening settings.

### 2. System Deployment and Troubleshooting
During the deployment and testing phase of the system, I applied various technical troubleshooting steps. Upon analyzing why the forwarded test logs were not reaching Wazuh, I detected that the **WSL2** virtual network (NAT) bridge was dropping `UDP/514` packets.

To overcome this issue:
- I bypassed the network layer by firing the test logs directly from within the Wazuh container, allowing me to test the configuration in isolation.
- Since the container image had a minimal structure and lacked the `logger` tool, I resolved the issue using the built-in redirection capabilities of the **Linux bash shell** to avoid creating any dependencies.
- Additionally, I observed that raw text did not trigger alerts because the Wazuh Decoder requires a standard Syslog header (Date, Hostname, etc.). Instead, I verified that the system successfully opened port `514` through the Manager's own startup logs.

Concluding this part of the work, I cleaned up the temporary routing rules I had added to the `rsyslog` service on WSL for testing purposes, restoring the laboratory environment to its original state to prevent future log conflicts.

### 3. System Vulnerability Management and CVE Analysis
In the second part of my work, I analyzed the scanning results of current security vulnerabilities (CVE) on machines with installed agents and planned the patching of the system. In this context, during the current scan I performed with the **Wazuh Vulnerability Detector** module on the `wsl-agent` (Ubuntu 24.04.4 LTS) machine, no findings were encountered at the **"Critical"** level.

As a result of my deduplication analysis, I detected **2 "High"** level vulnerabilities that require action.
